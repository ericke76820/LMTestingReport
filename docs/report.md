# 本地 LLM Agent 實測：工具呼叫與數值推理

> Windows 11 · RTX 5070 12 GB · OpenClaw 2026.10.6 · Ollama

## 摘要

  我在同一台桌機上，透過 OpenClaw 與 Ollama 測試四個本地模型，觀察它們能否讀取指定檔案、如實回報內容，以及正確估算模型權重的儲存空間。測試有兩個值得追查的結果：`gpt-oss:20b` 第一次讀檔呼叫未通過參數驗證，重試後仍答對；在另一題中，它則把「80 億」寫成「800 億」，後續算式雖然一致，答案卻差了十倍。這些案例顯示，只評分最終答案會漏掉有用的診斷資訊。

## 1. 測試目的與環境

 想要知道：本地模型放進 Agent 介面後，能否正確使用工具、根據資料回答，以及把自然語言中的數字一路帶到正確的計算結果。我的工作包括部署模型、設計題目與預期答案、檢查工具紀錄，以及比對模型回覆中的中間數值。

| 項目 | 設定 |
| --- | --- |
| 硬體 | NVIDIA GeForce RTX 5070（12 GB 顯存）、64 GB 系統記憶體 |
| 軟體 | Windows 11、OpenClaw 2026.10.6、Ollama |
| 測試模型 | `gemma4:12b`、`gpt-oss:20b`、`granite4:latest`、`ministral-3:latest` |
| 記錄方式 | OpenClaw 回覆、工具紀錄與介面顯示的總耗時 |

此報告是探索性實測。部分題目的措辭、推理選項或對話狀態不同；Ollama 版本、各模型的實際量化版本與 CPU／GPU 分配未在所有測試中完整記錄。`Ultra` 等名稱僅代表介面選項。表中的耗時是當次作業總耗時，可能含模型載入或工具重試，不能視為純推論速度。

## 2. 測試 A：讀取本地 JSON

**題目設計。** 指定工作區中的 `weather-test.json`，要求使用讀檔工具，回報台北的氣溫、天氣與紀錄編號，再判斷檔案是否含有高雄資料。題目要求以檔案為準，不上網、不猜測。以下是測試資料：

```json
{
  "台北": {
    "氣溫": "23.7°C",
    "天氣": "多雲",
    "紀錄編號": "WX-A17"
  }
}
```

**評分方式。** 台北三個欄位都須正確，並說明「檔案未提供高雄資料」。工具呼叫另外記錄：首次是否成功、是否重試，以及最後是否成功讀取。

| 模型 | 最終答案 | 可確認的讀檔紀錄 | 介面總耗時 |
| --- | --- | --- | --- |
| `gemma4:12b` | 正確 | 截圖未展開呼叫細節 | 31 秒 |
| `gpt-oss:20b` | 正確 | 2 次；首次驗證失敗，重試成功 | 41 秒 |
| `granite4:latest` | 正確（兩輪） | 每輪各 1 次成功 | 12 秒（Off）、8 秒（Ultra） |
| `ministral-3:latest` | 正確 | 截圖未展開呼叫細節 | 16 秒 |

**代表案例：重試成功。** `gpt-oss:20b` 首次呼叫 `read` 時帶入 `optional: false`，收到 `optional: must be equal to constant` 的驗證錯誤。第二次呼叫成功讀取資料，最終正確回覆台北三個欄位，也沒有捏造高雄資料。如果只看最終回答，這次與一次讀取就成功的案例都會被評為正確；若要評估 Agent 的運作，還應記錄首呼成功與錯誤恢復。

## 3. 測試 B：估算權重儲存空間

**題目設計。** 請模型簡述量化，估算 80 億參數分別以 FP16 與 4-bit 表示時的純權重空間，並說明是否等於實際顯存用量。部分追問要求先用阿拉伯數字寫出參數總數，再列算式。

**預期答案。** 1 億是 100,000,000，因此 80 億是 8,000,000,000。FP16 每個權重占 16 bits，也就是 2 bytes，純權重合計 **16 GB**；4-bit 每個權重占半個 byte，合計 **4 GB**。這裡用十進位 GB，且未計入量化格式的額外資料、KV 快取或推論暫存等開銷，也不代表所有權重實際都放在 GPU 上。

| 模型與輸入 | 觀察到的回答（FP16／4-bit） | 判讀 |
| --- | --- | --- |
| `gemma4:12b`，80 億 | 16 GB／4 GB | 這輪純權重估算正確。 |
| `gpt-oss:20b`，80 億 | 160 GB／40 GB | 列式時採用 80,000,000,000；後續乘法和 GB 換算符合這個錯誤的參數量。較早一輪曾答 1.6 GB／0.4 GB，當時沒有可供定位的算式。 |
| `gpt-oss:20b`，8,000,000,000 | 16 GB／4 GB | 這輪算對；同一對話的追問也正確列出位元與位元組換算。 |
| `granite4:latest`，80 億 | 0.2 GB／0.1 GB | 該輪把 FP16 與 4-bit 的每權重位元數都寫錯。另一輪改用完整數字，位元數寫對，容量換算仍有誤。 |
| `ministral-3:latest`，80 億 | 兩項估算皆錯 | 一輪列式時把參數量多寫一個零，且聲稱 4 個 4-bit 權重可放入 1 byte；正確是 2 個。 |
| `ministral-3:latest`，80,000,000,000（800 億） | 1,600 GB／400 GB | 開頭抄對數字，代入時多寫一個零。這題的參數量不同，正確值為 160 GB／40 GB。 |

**代表案例：算式揭露錯誤位置。** `gpt-oss:20b` 的 160 GB／40 GB 看起來像 GB 換算出錯，但列出的算式顯示，該輪錯在把「80 億」寫成了「800 億」。Ministral 的 800 億題則顯示，即使題目直接給完整數字，模型也可能在代入時改寫它。後續評分可逐項檢查「讀出的參數量」、「代入算式的參數量」、「每權重的位元數」與「最終單位換算」。

## 4. 限制與後續驗證

- **數字寫法：** 目前只能說在這些個案中看到了不同結果，還無法估計哪種寫法的答對率較高，也不能判定錯誤由模型量化引起。
- **複測方法：** 固定模型、推理選項及提示詞，僅替換 `80 億` 與 `8,000,000,000`；每次開新對話，兩種寫法各先測三次。逐次記錄原文、數值與算式，再報告答對次數。
- **工程應用：** 若要把流程放進 Agent，我會讓程式解析與驗證參數量，計算權重空間，再由模型解釋結果。對讀檔工具則保留呼叫與錯誤紀錄，以便區分參數驗證失敗、讀取失敗和回答與資料不符。

## 結論

這次實測建立了兩個可追查的案例：讀檔答對，可以同時伴隨一次工具呼叫失敗；容量估算答錯，也可能源自第一步輸入錯誤。把**工具紀錄、中間數值與最終答案**一起保存，讓我能指出哪一步需要改進，並為下一輪測試設計更明確的評分規則。
